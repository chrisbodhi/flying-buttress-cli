Flying Buttress · Eval Design Note

Three approaches to evaluating spec‑generated code.

Buttress generates implementations from SHA‑pinned specs via an LLM generate → verify → fix loop. To pick a model, set a temperature, and tune retry budgets, we need evals. Below are three approaches we can run today — from cheap and deterministic to qualitative and expensive.

Context 1 · Spec‑Test Pass Rate 2 · Golden Comparison 3 · LLM‑as‑Judge Comparison Recommendation

What we are evaluating

Each buttress add @org/pkg --generate call produces a single source file written to disk and then verified (tsc + the spec's declared test runner, today only for TypeScript). The unit of evaluation is therefore (spec, language, model, temperature, max_attempts) → output file. Every approach below scores that output along a different axis.

Knobs to sweep. Model family (e.g. gpt-4o-mini, claude-sonnet-4-6, claude-opus-4-7, a local Ollama model), temperature (0.0 / 0.2 / 0.7), MaxAttempts (1 / 3 / 5), and prompt variants (with/without test files in the system message). The chat request in internal/generate/generate.go does not currently set temperature — wiring that into LLMConfig is a prerequisite for any of these evals.

01Spec‑Test Pass Rate

Black‑box, automated, fully deterministic. The eval the verify loop already implies.

Reuse the verification step the CLI already runs as the eval harness. For every (spec, model, temperature) cell, run generate N times (e.g. 10 seeds), record per‑attempt outcomes, and aggregate into a single pass‑rate.

What we measure

  • pass@1: % of seeds passing on first attempt.
  • pass@k: % passing within MaxAttempts.
  • Attempts to green, conditional on passing.
  • Wall‑clock and token cost per success.
  • Stability: variance of pass@1 across seeds.

Why it fits Buttress

  • The spec format already requires tests — eval data is free.
  • No human labelling, no judge LLM, no rubric drift.
  • Surfaces feedback‑loop quality, not just one‑shot quality.
  • Detects regressions when we change prompts or upgrade models.

Recommended knob settings

# Run each cell with N=10 seeds; vary temperature per cell. temperature = 0.0 # primary — measures the model's "best guess" temperature = 0.7 # secondary — measures pass@k headroom with diversity max_attempts = 3 # the product default models = [gpt-4o-mini, sonnet-4-6, opus-4-7, qwen2.5-coder:7b] specs = curated set of ~30 specs spanning small/medium/large

Higher temperatures help pass@k by giving the fix loop a different draft to react to, but hurt pass@1. Reporting both makes the tradeoff legible.

Risks & mitigations. Flaky tests pollute scores — mark and quarantine any spec whose pass@1 standard deviation across seeds exceeds a threshold. Tooling errors (missing tsc, network installs) must be detected and excluded; the verifier already distinguishes these from real compile errors.

02Golden Implementation Comparison

Reference‑based, structural. Cheap to re‑run on every commit.

For each spec, hand‑author or hand‑audit a golden implementation per supported language. Score generated outputs against the golden along several structural dimensions, independent of whether tests pass.

What we measure

  • Public API match: same exported names, signatures, parameter shapes (parsed from AST).
  • Surface size: LOC ratio vs. golden — flags hallucinated helpers and dead code.
  • Cyclomatic complexity per exported symbol.
  • Normalised diff distance after stripping comments and renaming locals.
  • Dependency footprint: are unexpected packages imported?

Why it fits Buttress

  • Catches "tests pass but the implementation is a 400‑line monstrosity" failure modes that approach 1 misses.
  • Cheap and deterministic — no LLM call to grade.
  • Doubles as a regression watchdog when prompts change shape.

Recommended knob settings

temperature = 0.0 → 0.5 # sweep; higher temps drift further from golden judge = deterministic AST tools (tree-sitter, ts-morph) aggregation = weighted score; API match weighted 2× acceptance = ≥ 0.85 weighted score = "shaped like the golden"

Caveats. Goldens are opinions, not ground truth — a shorter, more idiomatic generation can score lower than a verbose copy of the golden. Use this as a shape filter, not a leaderboard. Maintaining goldens for every spec across multiple languages is the real cost; bootstrap by accepting a high‑confidence generation and editing it down.

03LLM‑as‑Judge with Rubric

Qualitative, multi‑dimensional. Captures what tests and ASTs can't.

Have a stronger model grade outputs from each cell against a fixed rubric. Use pairwise comparisons (A vs B) more than absolute scores — they're more reliable, and they convert into Elo or Bradley‑Terry rankings that survive rubric drift between runs.

Rubric dimensions

  • Correctness: does the code do what the spec says, beyond what the tests cover?
  • Idiomaticness: does it look like code a senior in this language would write?
  • Readability: naming, structure, comments.
  • Error handling: edge cases the tests miss.
  • Minimalism: no speculative abstractions.

Why it fits Buttress

  • Users will ultimately read this code — taste matters.
  • Surfaces hallucinations and over‑engineering that pass tests.
  • Cross‑family pairwise judging exposes whether a cheap model is "good enough" for routine specs.

Recommended knob settings

judge_model = claude-opus-4-7 # strongest available; grader ≠ generator judge_temperature = 0.0 # grader must be deterministic gen_temperature = [0.0, 0.3, 0.7] # the variable we're studying protocol = pairwise, blinded, randomised A/B order ranking = Bradley-Terry over ~200 comparisons per cell

Known biases. Judges prefer their own family (the "self‑preference" effect), prefer longer responses, and prefer the first option presented. Mitigate by (a) blinding language/model markers, (b) randomising A/B order, (c) running a second judge from a different family on a 10% sample to check for divergence, (d) excluding the generator's own family from judging its outputs.

How they compare

Dimension ① Spec‑Test ② Golden ③ LLM‑Judge
Signal type Functional correctness Structural conformance Qualitative judgment
Determinism High at T=0 High Medium
Cost per cell $ generation only $ generation only $$$ + judge tokens
Setup effort Low reuses verify High goldens per spec/lang Medium rubric + harness
Detects "passes tests, ugly code" No Yes Yes
Detects "looks great, doesn't work" Yes No Sometimes
Sensitive to temperature pass@1 falls, pass@k rises Drift increases with T Variance increases with T
Cross‑model comparable Directly Directly Via pairwise Elo

Recommendation

Run all three, but stagger them: ① Spec‑Test as the daily gate on every prompt or model change; ② Golden as a weekly shape check on a smaller curated set; ③ LLM‑Judge as a quarterly leaderboard refresh when picking the default model or negotiating with a new provider. Each one fails in a way the others catch, and only ① is cheap enough to run on every PR.

Concrete first step: add Temperature to LLMConfig and plumb it through chatRequest in internal/generate/generate.go, then stand up approach ① as a go test‑shaped harness under internal/evals/ with the existing TypeScript verifier.
